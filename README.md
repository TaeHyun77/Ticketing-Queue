**대기열과 참가열 분리**

이 시스템은 대기열과 참가열 두 개의 큐로 구성됩니다.

단일 큐로만 입장을 관리하면, 순서가 된 사용자를 대기열에서 제거하는 즉시 해당 사용자는 시스템 어디에도 존재하지 않게 됩니다. 이 상태에서 페이지 새로고침이나 네트워크 끊김이 발생하면 서버는 이 사용자가 입장 권한을 가진 사용자인지 판별할 수 없고, 동시 접속 제한도 까다로워집니다.

두 개의 큐를 분리함으로써 얻는 이점은 아래와 같습니다.

- 참가열의 크기가 곧 현재 이용 중인 사용자 수이므로 동시 접속 제어가 단순해집니다.
- 참가열 토큰에 TTL을 부여해 이탈한 사용자의 자리를 자동으로 회수할 수 있습니다.
- 각 큐가 순서 관리와 입장 권한 관리라는 명확한 책임을 가지게 되어 유지보수가 용이합니다.<br><br>

**승격 로직**

참가열의 최대 허용 인원은 서비스가 안정적으로 처리할 수 있는 부하 수준을 기준으로 설정합니다. 사용자가 대기열에 등록할 때 참가열에 여유가 있으면 바로 참가열로 삽입하고, 여유가 없으면 대기열에 삽입합니다. 이후 스케줄러가 3초 주기로 참가열의 잔여 수용량을 계산하여, 여유가 생긴 만큼 대기열의 사용자를 순서대로 참가열로 이동시킵니다.<br><br>


### 기존 단일 대기열 시스템에서의 변경점

---

기존 대기열 시스템에서는 대기열 상태 변경 시 DB 트랜잭션과 이벤트 전송의 정합성을 보장하기 위해 MySQL과 Kafka Debezium Connector를 활용한 CDC 방식으로 이벤트를 전달했습니다. 이 방식은 정합성 측면에서는 유리했지만, 대기열 상태 관리에 DB가 필수적이지 않음에도 데이터베이스에 의존하게 만든다는 한계가 있었습니다. 

개선된 시스템에서는 대기열 상태 관리에서 DB을 제거하고, 보다 경량화된 구조로 재설계하였습니다. 또한, Docker를 활용해 단일 서버 환경을 다중 인스턴스 기반의 분산 환경으로 확장함으로써, 장애 대응력과 가용성을 높였습니다.

Kafka는 분산 환경의 메시지 정합성을 위해 초기에 도입했으나, 실측 결과를 바탕으로 제거했습니다. 이 과정은 Kafka 도입과 제거 섹션에서 상세히 다룹니다.<br><br>

### 기능 구현
---
1. Redis ZSet 기반 대기열 시스템을 구현하고, 대기열과 처리열을 분리하여 상태 기반 큐 구조를 설계하였습니다.

2. SSE와 Kotlin Flow를 활용하여 대기열 상태를 클라이언트에 실시간으로 전달하는 이벤트 기반 구조를 구현하였습니다.

3. Redis Sentinel 기반 Replica 구조를 구성하여 장애 발생 시에도 서비스가 지속될 수 있도록 고가용성을 확보하였습니다.

4. 우선순위 및 처리량을 고려한 하이브리드 승격 로직을 구현하여 대기열 처리 효율을 개선하였습니다.

5. k6를 활용한 부하 테스트를 통해 RPS를 단계적으로 증가시키며 시스템 처리 한계를 측정하였습니다.<br><br>


### 분산 환경에서의 트러블 슈팅 💣
---
1. 서버 인스턴스별 메모리 기반 이벤트 스트림 분리로 인해 SSE 이벤트가 일부 클라이언트에 전달되지 않는 문제   

   → Redis Pub/Sub 기반으로 구조를 개선하여 모든 인스턴스 간 이벤트를 공유하도록 변경

2. 대기열 취소 상황에서 발생할 수 있는 문제

   → Redis Lua Script를 통해 대기열, 참가열에서의 제거를 원자적으로 함으로써 경쟁 상태를 해결

4. 분산 환경에서 인스턴스별 스케줄러가 독립적으로 실행되며 작업이 중복 수행되는 문제 

   → Redis 분산 락을 적용하여 단일 인스턴스에서만 스케줄링이 수행되도록 개선

5. Kafka Consumer 단건 처리 구조로 인한 성능 병목 및 Consumer Lag 증가 문제

    → 배치 리스너와 코루틴 병렬 처리를 도입하여 E2E p95 기준 1,648ms → 190ms로 약 8.7배 성능 개선하였습니다.
    → 이후 시스템 요구사항과 복잡도를 고려하여 Kafka 의존성을 제거하고 Redis 기반 구조로 재설계하였습니다.<br><br>

### 개선 사항
---
1. Redis Sentinel Failover 대응 설계

   Redis Sentinel failover로 인해 발생할 수 있는 데이터 유실, 락 유실, 이벤트 손실 문제를 분석하고, DB 락, 자동 재등록, 재동기화 로직 등을 통해 정합성을 유지하고 장애 상황에서도 복구가 가능하도록 설계했습니다.

3. SSE 이벤트 전달 구조 개선

   관계없는 사용자에게 전달되던 SSE 이벤트를 필터링해 불필요한 Redis 조회를 제거하고, 이벤트 종류를 명확히 분리했습니다.<br><br>

### Kafka 도입과 제거

---

**도입 배경**

티켓팅 서비스 특성상 공연 오픈 시각에 수만 명이 동시에 몰리는 상황을 전제로 설계했습니다.

- 목표 처리량 : 1,000 RPS
- 목표 지연 시간 : E2E 1초 이하<br><br>

분산 환경에서 여러 인스턴스가 동시에 요청을 처리할 때 순서 정합성 보장, 서버 장애 시 메시지 유실 방지, 급격한 트래픽 급증 시 부하 완충이라는 세 가지 목적으로 Kafka를 도입하였습니다.<br><br>

초기 아키텍처는 아래와 같습니다.
```
사용자 → Nginx → Spring WebFlux (3 인스턴스) → Kafka → Consumer → Redis
```
<br>

**벤치마크 테스트 결과 (Kafka 적용)**

| RPS | avg (ms) | p95 (ms) | E2E p95 (ms) | E2E max (ms) | 처리량 (/s) |
| --- | --- | --- | --- | --- | --- |
| 100 | 34.23 | 59.08 | 67 | 136 | 74.1 |
| 200 | 48.03 | 101.23 | 197 | 395 | 154.0 |
| 300 | 44.42 | 95.56 | 190 | 378 | 230.9 |
| 400 | 74.44 | 158.97 | 346 | 589 | 307.8 |
| 500 | 111.81 | 278.52 | 544 | 842 | 400.0 |
| 600 | 249.94 | 773.41 | 1,197 | 1,977 | 461.8 |

<br><br>

모든 구간에서 성공률은 100%였지만 RPS 600에서 E2E p95가 1.2초를 초과하며 목표였던 1초 이하를 달성하지 못했습니다. 또한 RPS가 증가할수록 HTTP 응답 시간과 E2E 시간의 격차가 비선형적으로 확대되었습니다.<br><br>

**원인 파악**

Consumer의 배치 처리(최대 200건)로 Consumer Lag은 크게 발생하지 않았습니다. 즉, 처리 속도 문제가 아닌 Kafka를 경유하는 구조 자체가 만드는 지연이 근본 원인이었습니다.

`acks=all` 설정으로 인해 produce 단계에서 3개 브로커의 복제 완료까지 대기하는 지연이 발생하고, produce 완료 후에도 Consumer가 다음 poll을 수행하기까지의 비동기 간극이 추가됩니다. RPS가 올라갈수록 produce 단계의 경합이 심해지면서 이 지연은 비선형적으로 증가했습니다.<br><br>

**도입 이유 재검증**

- **영속성** : 실제 상태는 Redis에 저장되므로 Redis 장애 시 Kafka 재처리도 실패하는 구조여서 영속성의 실효성이 낮았습니다.

- **재시도** : Redis Sentinel failover 시간에 맞춰 재시도 간격을 늘리면 해당 파티션의 후속 메시지 처리가 전부 멈추는 문제가 발생하여, 실시간 대기열 시스템에서는 치명적이었습니다.

- **부하 완충** : 1,000 RPS 기준 Redis에 발생하는 연산량은 Redis 최대 처리량의 약 9% 수준에 불과하여 완충이 필요한 상황 자체가 아니었습니다.<br><br>

결과적으로 Kafka는 확장성을 만든 것이 아니라 지연과 복잡도를 만드는 계층이 되었습니다.<br><br>

**대기열 등록 과정**<br>

1. 클라이언트는 대기열 등록 요청 시 대기열 식별자인 queueType, 사용자 식별자인 userId를 서버로 전달합니다.

    서버는 요청 도착 시각을 timestamp로 기록하며, 클라이언트와 SSE 연결을 수립합니다.

2. Redis SET NX 명령어로 중복 요청을 검증한 뒤, userId를 member로, timestamp 기반의 score를 Redis Sorted Set에 삽입합니다. zadd 명령어의 원자성에 의해 대기열 순서가 요청 시각 기준으로 자동 정렬됩니다.

3. Redis Pub/Sub을 통해 대기열 갱신 이벤트를 모든 서버 인스턴스에 전파하여, 각 서버가 동일한 대기열 상태를 공유할 수 있도록 합니다.

    클라이언트는 SSE 연결을 통해 대기열 상태가 변경될 때마다 실시간으로 갱신된 정보를 수신합니다.

4. 대기열 시스템은 대기열과 참가열 두 영역으로 구성되며, 스케줄러가 주기적으로 대기열에서 일정 인원을 참가열로 승격시킵니다. 참가열로 승격된 사용자는 타겟 페이지에 접근할 수 있는 권한을 획득하며, 클라이언트는 해당 페이지로 이동합니다.

5. 참가열로 승격된 사용자에게는 queueType과 userId 기반의 접근 토큰을 생성하여 클라이언트 쿠키에 저장합니다. 이후 사용자가 타겟 페이지에 진입하면, 서버는 동일한 방식으로 토큰을 재생성하여 클라이언트가 전달한 토큰과 비교하고, 참가열에서의 TTL 만료 여부를 함께 확인하여 사용자의 접근 권한을 검증합니다.
