# Integrated Queueing System

### 프로젝트 설명

---

티켓팅처럼 특정 시간에 수만 명이 동시에 접속하는 상황을 처리하기 위한 **분산 대기열 시스템**입니다. 기존의 단일 서버 기반 시스템을 Docker 기반 다중 인스턴스 환경으로 확장하고, Redis Sentinel을 통한 고가용성을 확보했습니다. 대기열 통과 후 진입하는 예약 시스템(별도 프로젝트)을 함께 통합하여, 대기열 → 예약으로 이어지는 전체 흐름을 하나의 인프라에서 구성했습니다.

**구현 과정 개인 블로그**

https://velog.io/@ayeah77/series/%EB%8C%80%EA%B8%B0%EC%97%B4-%EC%8B%9C%EC%8A%A4%ED%85%9C-%EA%B0%9C%EC%84%A0

### 기술 스택

---

Backend : Spring WebFlux, Kotlin, Coroutine

Frontend : React, JavaScript

Cache : Redis (Sentinel 기반 Master-Replica)

Infra : Docker, Nginx, Redis Sentinel

ETC : SSE, Redis Pub/Sub, Redis Lua Script, Prometheus, Grafana, k6

> Kafka는 초기에 도입했다가 실측 결과를 바탕으로 제거했습니다. 과정은 [Kafka 도입과 제거](#kafka-도입과-제거) 섹션에서 다룹니다.

### 아키텍처

---

<p align="center"><img width="1536" height="1024" alt="아키텍처" src="https://github.com/user-attachments/assets/9f2c841b-1821-4756-b789-cfe05282b9a4" />

```
사용자 요청 → Nginx(라운드로빈) → 앱 인스턴스 3대 (WebFlux)
            → Lua 스크립트로 대기열/참가열 원자 처리 (Redis Master)
            → Redis Pub/Sub으로 전 인스턴스에 이벤트 전파 → SSE로 클라이언트 실시간 알림
```

- 앱 인스턴스 3대는 Nginx 라운드로빈으로 부하 분산되며, 시작 시 Redis Pub/Sub 채널을 구독하여 이벤트를 수신할 준비를 합니다.
- Redis는 Master 1대 + Replica 2대 + Sentinel 3대로 구성되어 장애 시 자동 failover 됩니다.
- 예약 서비스 2대와 MySQL은 대기열 통과 후의 예약 처리를 담당합니다.
- Prometheus + Grafana로 애플리케이션/Redis 지표를 수집·시각화합니다.

### Quick Start

---

```bash
# 3노드 분산 환경 (앱 3대 + Redis Sentinel + Nginx + 모니터링 + 예약 서비스)
docker compose up -d --build

# 부하 테스트용 1노드 환경
docker compose -f docker-compose.1node.yml up -d --build
```

진입점은 Nginx(`http://localhost:8079`)이며, 요청은 앱 인스턴스 3대로 분산됩니다.

### 기존 단일 대기열 시스템에서의 변경점

---

기존 대기열 시스템에서는 대기열 상태 변경 시 DB 트랜잭션과 이벤트 전송의 정합성을 보장하기 위해 MySQL과 Kafka Debezium Connector를 활용한 CDC 방식으로 이벤트를 전달했습니다. 이 방식은 정합성 측면에서는 유리했지만, 대기열 상태 관리에 DB가 필수적이지 않음에도 데이터베이스에 의존하게 만든다는 한계가 있었습니다.

개선된 시스템에서는 대기열 상태 관리에서 DB를 제거하고, Redis를 단일 진실 원천으로 삼는 경량화된 구조로 재설계하였습니다. 또한 Docker를 활용해 단일 서버 환경을 다중 인스턴스 기반의 분산 환경으로 확장함으로써, 장애 대응력과 가용성을 높였습니다.

### 기능 구현

---

1. Redis ZSet 기반 대기열 시스템을 구현하고, 대기열(wait)과 참가열(allow)을 분리하여 상태 기반 큐 구조를 설계하였습니다.

2. 중복 검증·삽입 위치 판단·삽입을 하나의 Lua 스크립트로 묶어 원자적으로 처리함으로써, 다중 인스턴스 환경에서도 경쟁 상태 없이 선착순이 보장되도록 구현하였습니다.

3. SSE와 Kotlin Flow를 활용하여 대기열 상태를 클라이언트에 실시간으로 전달하는 이벤트 기반 구조를 구현하였습니다.

4. Redis Sentinel 기반 Replica 구조를 구성하고, failover 시 데이터 유실 창을 제한하는 설정과 클라이언트 자가 복구 API를 더해 고가용성을 확보하였습니다.

5. 참가열 TTL 만료 정리 → 빈자리 계산 → 대기열 선두 승격을 단일 Lua 스크립트로 원자 처리하는 승격 스케줄러를 구현하고, Redis 분산 락으로 다중 인스턴스 중복 실행을 방지하였습니다.

6. k6를 활용한 부하 테스트를 통해 RPS를 단계적으로 증가시키며 1노드/3노드 처리 한계를 실측하였습니다. ([부하 테스트 결과](#부하-테스트-결과))

### 대기열 등록 과정

---

1. 클라이언트는 대기열 등록 요청 시 대기열 식별자인 `queueType`, 사용자 식별자인 `userId`를 서버로 전달하며, 서버와 SSE 연결을 수립합니다.

2. 서버는 `enqueue-or-allow.lua` 단일 Lua 스크립트로 **중복 검증 → 참가열 만료 정리 → 삽입 위치 판단 → 삽입**을 원자적으로 수행합니다.

   - 대기열 score는 timestamp가 아닌 **이벤트별 단조 증가 시퀀스**(`INCR queue:seq:{queueType}`)를 사용하여, 동시 요청 간 순서가 유일하게 결정됩니다.
   - 참가열에 여유가 있어도 **대기자가 한 명이라도 있으면 신규 진입자는 대기열로** 들어갑니다. 빈자리는 반드시 대기열 선두가 채우도록 하여 선착순(FIFO)을 보장합니다.

3. Redis Pub/Sub을 통해 대기열 갱신 이벤트를 모든 서버 인스턴스에 전파하고, 각 인스턴스는 자신과 연결된 클라이언트에게 SSE로 갱신된 순번을 실시간 전달합니다.

4. 승격 스케줄러(3초 주기, Redis 분산 락으로 단일 인스턴스 실행)가 `schedule-promote.lua`로 **참가열 만료 정리 → 빈자리 계산 → 대기열 선두 승격**을 원자적으로 수행합니다. 참가열로 승격된 사용자는 타겟 페이지에 접근할 수 있는 권한을 획득합니다.

5. 참가열로 승격된 사용자에게는 `queueType`과 `userId` 기반의 접근 토큰을 생성하여 클라이언트 쿠키에 저장합니다. 이후 사용자가 타겟 페이지에 진입하면, 서버는 동일한 방식으로 토큰을 재생성하여 클라이언트가 전달한 토큰과 비교하고, 참가열에서의 TTL 만료 여부를 함께 확인하여 접근 권한을 검증합니다.

### 분산 환경에서의 트러블 슈팅 💣

---

1. **인스턴스별 메모리 기반 이벤트 스트림 분리로 SSE 이벤트가 일부 클라이언트에 전달되지 않는 문제**

   → Redis Pub/Sub 기반으로 구조를 개선하여 모든 인스턴스 간 이벤트를 공유하도록 변경

2. **timestamp 기반 score의 동시 요청 충돌 문제** — 동일 밀리초에 도착한 요청들의 score가 같아져 대기 순서가 비결정적으로 정렬되는 문제

   → 이벤트별 `INCR` 단조 증가 시퀀스를 score로 사용하여 순서를 유일하게 결정

3. **신규 진입자의 참가열 빈자리 선점 문제** — 참가열에 여유가 생긴 순간 신규 진입자가 먼저 온 대기자를 추월해 직행하는 선착순 위반

   → 대기자가 존재하면 신규 진입자는 무조건 대기열로 보내고, 빈자리는 스케줄러가 대기열 선두부터 채우도록 Lua 스크립트에서 규칙화

4. **대기열 취소와 승격 스케줄러 간 Race Condition** — 취소 처리 도중 스케줄러가 해당 사용자를 승격시키면 취소가 유실되는 문제

   → 대기열/참가열 양쪽 제거를 `cancel-user.lua`로 원자화하여 중간 상태 자체를 제거

5. **인스턴스별 스케줄러가 독립적으로 실행되며 승격 작업이 중복 수행되는 문제**

   → Redis 분산 락을 적용하여 단일 인스턴스에서만 스케줄링이 수행되도록 개선

6. **SSE 이벤트 유실 지점** — 느린 소비자에 의한 sink 오버플로 드랍, Pub/Sub 스트림이 예외 없이 종료되면 재구독되지 않아 알림이 영구 중단되는 문제

   → sink 오버플로 정책을 `DROP_OLDEST`로 변경하고, Pub/Sub 스트림 종료 시 무조건 재구독하도록 수정

### 개선 사항

---

1. **Redis Sentinel Failover 유실 대응 설계**

   Sentinel failover 시 아직 복제되지 않은 쓰기가 유실될 수 있는 문제를 세 겹으로 방어했습니다.

   - `min-replicas-to-write 1` + `min-replicas-max-lag 10` : 복제본이 따라오지 못하면 마스터가 쓰기를 거부하여 유실 창 자체를 제한
   - AOF + 데이터 볼륨 영속화 : 재시작된 빈 마스터가 재동기화로 전체 데이터를 지워버리는 시나리오 차단
   - 통합 상태 조회 API(`GET /queue/get/status` → `WAIT` / `ALLOW` / `NONE`) : 유실이 발생하더라도 클라이언트가 자신의 상태를 재확인하고 재등록할 수 있는 자가 복구 경로 제공

2. **SSE 이벤트 전달 구조 개선**

   관계없는 사용자에게 전달되던 SSE 이벤트를 필터링해 불필요한 Redis 조회를 제거하고, 이벤트 종류(순번 갱신 / 승격 확정 / 취소 / 에러)를 명확히 분리했습니다.

### Kafka 도입과 제거

---

분산 환경에서 인스턴스 간 메시지 정합성을 위해 초기에 Kafka를 도입했습니다. 운영 중 Consumer 단건 처리 구조로 인한 병목과 Consumer Lag 증가 문제가 발생했고, 배치 리스너와 코루틴 병렬 처리를 도입하여 E2E p95 기준 **1,648ms → 190ms로 약 8.7배** 개선했습니다.

그러나 개선 이후에도 근본적인 의문이 남았습니다. 대기열 상태의 단일 진실 원천이 Redis인 구조에서, 이벤트 전파를 위해 브로커를 한 번 더 경유하는 것은 지연과 운영 복잡도(브로커/커넥터 관리)만 더하는 홉이었습니다. 이벤트 전파는 Redis Pub/Sub으로 충분히 대체 가능했기에, 실측 검증 후 Kafka 의존성을 제거하고 Redis 기반 구조로 재설계했습니다.

### 부하 테스트 결과

---

k6로 대기열 등록 요청의 RPS를 500 → 3,000까지 단계적으로 올리며 1노드/3노드 구성을 각각 3회 측정한 중앙값입니다. (전 구간 성공률 100%, 실패·중복 0건)

| 구성 | RPS | http p95 | http p99 | 비고 |
|---|---|---|---|---|
| 1노드 | 2,500 | 84ms | 265ms | 안정 구간 |
| 1노드 | 3,000 | 443ms | 1,174ms | 지연 급증 — 처리 한계 부근 |
| 3노드 | 3,000 | 286ms | 599ms | 동일 부하에서 tail latency 완화 |

- 1노드는 RPS 2,500 → 3,000 구간에서 p95가 84ms → 443ms로 급증하며 처리 한계에 도달합니다.
- 스파이크 테스트(순간 3,000 RPS 유입)에서도 87,931건 전량 성공(성공률 100%, p95 335ms)을 확인했습니다.
- 단, 테스트는 단일 머신(Apple M4) 위에 3노드를 함께 띄운 구성이라 노드 간 코어 경합이 존재하며, 3노드의 수평 확장 효과는 실제 분산 배포 대비 보수적으로 측정된 값입니다.
