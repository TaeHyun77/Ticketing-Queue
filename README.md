### 프로젝트 설명

---

티켓팅처럼 트래픽이 단시간에 집중되는 상황을 대기열로 제어하는 시스템으로, SSE 실시간 순번 알림/Redis Sentinel 페일오버/Lua 원자 스크립트를 통해 정확성과 가용성을 함께 확보했습니다.<br><br>

**왜 분산 환경으로 설계했는지**

목표는 동시접속 4-5만이었지만, 부하 테스트 결과 단일 2코어 서버에서는 약 1.5만-2만 연결 부근에서 CPU가 포화되는 한계가 확인되었고, 이에 따라 서버를 여러 대로 나누는 수평 확장을 고려하게 되었습니다.

다만, 서버를 여러 대로 분산하면 각 서버가 독립적인 Flow를 가지므로, 한 서버에서 발생한 승격 이벤트가 다른 서버의 SSE 연결에는 전달되지 않는 문제가 발생하였는데, 이 문제는 뒤에서 별도로 다루겠습니다.

또한, 서버를 여러 노드로 분산함으로써 단일 노드 장애가 전체 서비스 장애로 이어지지 않는 가용성도 확보할 수 있습니다.<br><br>

<img width="1200" height="230" alt="ㄴㄴㅇㅁ" src="https://github.com/user-attachments/assets/827c35f0-26a9-4a39-9541-e56084066d00" />


1. 등록 및 SSE 연결

   클라이언트가 /register로 queueType, userId를 전송하면, 등록 결과(wait 큐 진입 / allow 큐 직행)를 응답으로 확인합니다. 이후 /stream에 SSE를 연결해 상태 변경을 실시간 수신합니다.

2. Lua 원자 처리

   등록은 단일 Lua 스크립트로 원자 처리됩니다. ZSCORE로 중복을 체크하고, INCR로 score를 발급해 선착순 정렬을 보장합니다. 참가열 여유가 있고 대기자가 없을 때만 allow 큐에 직행하며, 그 외에는 wait 큐에 삽입합니다.

3. 스케줄러 승격 및 SSE 팬아웃

   스케줄러가 주기적으로 wait 큐 선두를 Redis Pub/Sub으로 변경 신호를 서버 간 전파하고, 각 서버가 자신의 StateFlow에 emit하여 allow 큐로 승격합니다.

   StateFlow는 queueType별로 분리되며, conflation으로 최신 payload만 유지합니다.
   
   - 승격된 사용자 : ZRANK 없이 confirmed 이벤트를 즉시 전송합니다.
   - 나머지 대기자 : ZRANK 없이 누적 승격 인원(admittedThrough)만 담은 moved 이벤트를 팬아웃합니다. 클라이언트는 연결 시 init 이벤트로 수신한 앵커값(초기 순번 R0, 초기 누적 승격 인원 A0)으로 'rank = R0 - (admittedThrough - A0)'를 로컬 계산합니다. admittedThrough는 단조 증가 절대값이므로 StateFlow conflation으로 중간 이벤트가 유실되어도 최신 값 하나로 순번을 복원할 수 있습니다.

4. HMAC 토큰 기반 접근 제어

   승격된 사용자에게 queueType:userId를 입력으로 한 HmacSHA256 토큰을 발급해 쿠키에 저장합니다. 실제 서비스 접근 시 토큰을 재생성해 비교하고, allow 큐 score(expireAt)가 현재 시각을 초과했는지로 TTL 만료도 함께 확인합니다.<br><br>

### 주요 기능
---
1. Redis ZSet 기반 대기열과 참가열을 분리 설계하여, 대기 순서 관리와 입장 제어를 각각의 정렬 집합으로 처리하는 상태 기반 큐 구조를 구현했습니다.
   
2. SSE와 Kotlin Flow( StateFlow )로 대기열 상태를 실시간 전달하고, Redis Pub/Sub으로 변경 이벤트를 전 인스턴스에 팬아웃하는 이벤트 기반 구조를 구현했습니다.
   
3. Redis Sentinel + Replica 구성에 AOF 영속화와 min-replicas-to-write 설정을 통해, 마스터 장애 시 자동 페일오버와 데이터 유실 최소화로 고가용성을 확보했습니다.

4. 참가열 승격 시 queueType:userId HMAC-SHA256 토큰을 발급, 쿠키 저장하고, 타겟 페이지 진입시 토큰 재생성 비교 + 참가열 TTL 만료 확인으로 무단 접근을 차단하였습니다.<br><br>

### 개선 사항
---
1. SSE 이벤트 전달 구조 개선

   초기에는 승격 이벤트만 브로드캐스트하고, 각 구독자가 Redis ZRANK로 자신의 순번을 재조회했습니다. 이로 인해 팬아웃마다 대기자 수만큼 Redis 왕복이 발생해 전체 비용이 O(W²/k)까지 증가했습니다.

   이를 절대 커서로 변경하여 승격 1회당 Redis 왕복을 N회에서 1회로 줄이고 전체 비용을 O(W/k)로 낮췄습니다.

   또한, 절대 커서는 최신 값만으로 상태를 복원할 수 있어 이벤트 유실을 허용할 수 있으므로, 생산자 블로킹을 감수하던 SharedFlow에서 StateFlow로 전환했습니다.

### 트러블 슈팅 💣
---
1. 다중 인스턴스 환경에서 SSE 이벤트 유실

   분산 서버 환경에서는 각 서버가 SSE 이벤트를 인메모리로 관리하기 때문에, 한 서버에서 발생한 대기열 변경 이벤트가 다른 서버에 연결된 클라이언트에게 전달되지 않는 문제가 발생했습니다.
   
   → Redis Pub/Sub을 통해 변경 이벤트를 모든 인스턴스에 전파하고, 각 인스턴스가 자신에게 연결된 SSE 구독자에게만 이벤트를 전달하도록 구성했습니다. 이를 통해 팬아웃 부담을 노드별 O(N/k)로 분산하여 단일 노드의 CPU 한계를 넘어 수평 확장할 수 있도록 했습니다.

2. 취소와 승격 스케줄러의 Race Condition

   사용자 취소와 승격이 동시에 수행되면 조회와 삭제 사이에 사용자가 승격되어 대기열과 참가열에 동시에 존재하는 정합성 문제가 발생했습니다.
   
   → Redis Lua Script를 통해 대기열과 참가열의 제거를 원자적으로 처리하여 경쟁 상태를 제거함으로써 해결하였습니다

3. 다중 인스턴스 스케줄러의 중복 실행

   모든 인스턴스가 동일한 승격 스케줄러를 실행하면서 승격 작업이 중복 수행되는 문제가 발생했습니다.
   
   → Redis 분산 락을 적용하여 하나의 인스턴스만 승격 작업을 수행하도록 하여 해결하였습니다.

4. 선착순 역전 문제

   참가열에 빈자리가 생겼을 때 대기자가 존재함에도 신규 요청자가 먼저 참가열에 진입하는 문제가 발생했습니다.
   
   → 대기자 우선 승격 규칙을 적용하여 항상 대기열 선두 사용자가 먼저 참가열로 이동하도록 하여 해결하였습니다.<br><br>

### 부하 테스트 / 성능 검증
---
단일 노드에서 SSE 연결을 장시간 유지하고, 연결 수 증가에 따른 성능 한계와 안정성을 검증했습니다.

1. 15,000 동시 연결 Soak 테스트

   1시간 동안 FD/Heap/RSS가 안정적으로 유지되었으며, 종료 후에도 자원이 정상적으로 회수되어 누수 없이 안정적으로 연결을 유지할 수 있음을 확인했습니다. 총 840만 건의 팬아웃 이벤트를 처리했으며, 에러는 발생하지 않았습니다.

2. SSE 연결 용량 측정

   팬아웃 비용이 연결 수에 비례하면서 2코어 CPU가 약 15K~20K에서 포화되었습니다. 특히 연결 유지보다 새로운 연결을 생성하면서 동시에 팬아웃하는 과정에서 부하가 크게 증가했으며, 10K에서 55초, 20K에서 약 270초까지 연결 생성 시간이 증가했습니다.
  
3. 비정상 종료 및 Backpressure 검증

   RST로 연결을 강제 종료해도 FD가 정상적으로 회수되었으며, 느린 소비자 10%를 포함한 상황에서도 메모리 증가 없이 안정적으로 처리했습니다.

4. 측정 신뢰성 검증

   클라이언트 ELD, CPU steal, NTP 오차를 확인해 부하 생성기나 인프라 환경으로 인한 측정 왜곡을 배제했습니다.<br><br>

결론적으로 단일 2코어 서버는 약 15K~20K에서 CPU 한계에 도달했으며, 수만 명의 동시 연결을 처리하려면 SSE 연결을 여러 노드로 분산하고 Pub/Sub를 통해 이벤트를 전파하는 분산 구조가 필요하다는 정량적 근거를 확보했습니다.<br><br>
